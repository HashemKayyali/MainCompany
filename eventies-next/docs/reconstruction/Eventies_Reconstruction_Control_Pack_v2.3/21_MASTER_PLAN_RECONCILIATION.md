## Headline verdict
The Master Plan and the Control Pack **agree on the destination** (Next.js App Router, Supabase preserved, Cloudinary single pipeline, server-first public pages, client islands, SSR cookie auth, /ar multilingual SEO, Expo-ready contracts, no monorepo yet). They **disagree on the road**: the plan's two-stage Compatibility→Native strategy is superseded by Freeze-and-Reconstruct (ADR-02) — the compatibility stage would port exactly the subsystems both audits ruled must die (MutationObserver i18n, dual-storage auth adapter, DataContext triple fallback). Roughly 80% of the plan's content is KEPT (often in a more precise V2.1 form); the strategic spine and a handful of technical rulings are SUPERSEDED with evidence.

## The seven mandated conflict rulings
**A. Migration strategy — FINAL: Freeze-and-Reconstruct (ADR-02).** The Compatibility→Native two-stage is retired entirely; no compat stage exists in any phase prompt. What the plan wanted from Stage A (early runnable checkpoint, incremental risk) is delivered differently: frozen Vite stays production + per-route-group cutover + per-phase rollback tags. One strategy is active.

**B. Design-change restriction — FINAL 5-way rule (Constitution §1 amendment):** (1) Product/visual design: **preserved** — no redesign during reconstruction (plan rule kept; admin interiors behavior-parity only). (2) Architecture reconstruction: **sanctioned** per Preserve/Deletion ledgers — weak implementation does not survive. (3) Security hardening: **sanctioned additive** (MFA, Turnstile, trusted boundaries — the plan's own §18 demands them). (4) Performance architecture: **sanctioned when a budget/gate requires it** (gallery batching is the plan's own rule 9). (5) Intentional UX changes: **⛔ human approval required**, logged (e.g. remember-me behavior per ADR-17).

**C. Folder structure — FINAL: V2.1 authoritative.** `[locale]` segment (not a parallel `ar/` tree), route groups, `src/i18n/{routing,navigation,request}.ts`, `proxy.ts`, `server/` with `server-only` + import zones. Adopted from the plan: `manifest.ts` (SEO-015). The plan's own caveat ("الهيكل تنظيمي وليس إذناً") concedes authority.

**D. Realtime — FINAL rule (ADR-06 amended):** Everything currently stays on **Postgres Changes** with the 09 reliability protocol; **no feature migrates now**. Broadcast becomes justified only if measured: sustained realtime latency degradation on the admin inbox, subscriber-count growth past Postgres-Changes comfort (many concurrent clients on one topic), or a future fan-out feature (public presence/live events). Any move = new ADR + parity tests.

**E. Images — FINAL: no contradiction remains.** "Single Cloudinary pipeline" (plan) and per-surface delivery (V2.1) are the same decision at different layers: Cloudinary is the ONLY transformation/optimization source (plan rule 3 intact — the custom loader bypasses Vercel's optimizer entirely); delivery components differ per surface (`next/image`+loader on catalog/marketing, ported `<img srcset>` in admin/lightbox). The V1 "never use next/image" slogan was already retracted in V2 §16/ADR-08 — verified absent from the pack.

**F. Database-change policy — FINAL rule (adopted verbatim into Constitution §4):** *No framework-driven database churn. Database changes are allowed only when they enforce justified business, integrity, security, localization, or reliability requirements* — and only as additive, DBMIG-piped, human-gated migrations (frozen-Vite compatible until P7). The V2.1 waves (`_ar`, idempotency, message IDs, CHECKs, rate limits, app_events, AAL enforcement) each cite their justification class.

**G. Admin architecture — FINAL:** dynamic, no public cache; **server-gated shell** (session→role→AAL2) as early screen; **CSR interiors** ported behavior-parity (ADR-04); **authoritative authorization at the mutation boundary** per 05 §Destructive-Operation Boundary Matrix + BYPASS suite; MFA/recent-auth enforced at that boundary, never by layout/UI alone. No pack text implies layout-gate sufficiency (verified; Constitution §3 states it explicitly).
