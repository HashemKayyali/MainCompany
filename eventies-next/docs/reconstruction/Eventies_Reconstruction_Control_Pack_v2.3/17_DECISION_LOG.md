# 17 — DECISION LOG (ADR format)
All contested questions from Audit V1, Review V2, and pack reconciliation. These rulings bind every other file.

**ADR-01 — Framework.** Q: Vite SPA vs Next.js App Router vs RR7 Framework Mode vs Astro. Decision: **Next.js App Router.** Evidence: four structural SPA limits (Arabic indexability, deploy-coupled freshness via `scripts/prerender-seo.mjs`, soft-404 catch-all in `vercel.json`, no trusted server boundary for bot defense). Tradeoff: 6–10 wks rebuild + cutover window. Supersedes V1's "stay on Vite". Revisit: never during this project.

**ADR-02 — Strategy.** Q: fix-Vite-first (A) vs freeze-and-reconstruct (B) vs pure strangler (C) vs domain rebuild (D). Decision: **B+D build, C as deployment mechanism** (route-group rewrites, rollback = restore rewrite). Evidence: V2 §4 matrix; i18n-on-Vite is throwaway plumbing. Tradeoff: two apps share one DB until P7 → no-destructive-migration window rule.

**ADR-03 — i18n.** Q: next-intl vs custom; where built. Decision: **next-intl, built directly in Next (P1)**; `localePrefix: 'as-needed'` (EN URLs unchanged, AR at `/ar/*`); entity content moves to DB `*_ar` columns; DOM MutationObserver engine banned. Supersedes V1 "Phase 0a on Vite". Revisit: only if next-intl blocks a hard requirement in P1 (fallback: custom typed dictionaries, same URL model).

**ADR-04 — Admin rendering.** Decision: server-gated shell (session→role→MFA in layout), **interior pages ported as client components** — the single sanctioned page-root `'use client'` exception. Evidence: 17 dense interactive grids + realtime; RSC adds no value; V1 and V2 agree.

**ADR-05 — Mutation boundaries.** Q: Server Actions vs Route Handlers vs direct RPC vs Edge Fn. Decision: per-mutation matrix (V2 §11): **Route Handlers** for the 3 abuse-sensitive public forms (Zod+Turnstile) and for `/api/revalidate`; **direct RPC** for authenticated app writes (requests, quotes, chat, admin CRUD); **Edge Fn** stays for Cloudinary; **Server Actions** cosmetic-only, never an auth boundary. Resolves V1's blanket ban vs the pressure to server-wrap everything.

**ADR-06 — Realtime transport.** Decision: **stay on Postgres Changes**; add the reliability protocol (`09`): stable channel names (uuid suffix removed), subscribe→buffer→snapshot→replay, idempotent reducers, client message IDs. Revisit: if superadmin inbox latency degrades measurably.

**ADR-07 — Catalog data ownership.** Decision: **server-owned** (ISR + tags + TTL backstop). `DataContext` triple fallback (module defaults → localStorage snapshot → live) is REMOVE for catalog; cart/drafts remain client-owned. No outbox: failed revalidation → admin-visible warning + retry + ≤1h TTL self-heal. Revisit: recurring `revalidate.failed` telemetry.

**ADR-08 — Images.** Decision: `next/image` **with custom Cloudinary loader** delegating to `toCloudinaryTransformUrl` (Vercel optimizer bypassed → no billing) for catalog/marketing; ported `<img srcset>` components inside admin/lightbox internals. Retracts V1's blanket ban. New uploads Cloudinary-only; legacy Supabase Storage estate read-only via existing render fallback.

**ADR-09 — Auth.** Decision: `@supabase/ssr` cookie sessions; Route Handler callback; remember-me redesigned as cookie lifetime; dual-storage adapter deleted; **one bridge (BRIDGE-01)** for session adoption; **Phase 1B prototype must pass its 8 questions before any auth-dependent route cutover**. Admin: TOTP MFA + AAL2 in layout + recent-auth (≤15 min) for destructive ops.

**ADR-10 — Sitemap.** Decision: KEEP+HARDEN — port `api/sitemap.ts` ~verbatim to a Route Handler; add `/custom-builds`, hreflang alternates (post-P2), category-visibility filter verification. Corrects V1 F-4 ("possibly broken") with V2 evidence (file exists, well-built).

**ADR-11 — Rate limits.** Decision: Supabase native limits are the base; app-level adds identifier-centric dimensions + Turnstile triggers at the new server boundary; **all thresholds provisional** until calibrated per `05` §Calibration. No Vercel WAF unless telemetry demands.

**ADR-12 — Monorepo/Expo.** Decision: no monorepo now. `src/shared/` conventions (`03`) keep schemas/types/contracts extraction-ready; split when Expo work actually starts.

**ADR-13 — Observability.** Decision: Sentry (scrubbed) + Vercel Analytics/Speed Insights + `app_events` structured events + 6 alert rules (V2 §18). No enterprise APM.

**ADR-14 — Validation.** Decision: Zod at server trust boundaries (`src/shared/schemas`), client forms mirror for UX, DB constraints enforce invariants independently (add CHECKs: quantities, date ordering, message lengths — REQ/CHAT tasks). TypeScript types are never a substitute.

**ADR-15 — Master Plan reconciliation (CLOSED at V2.2).** The Master Plan was received at the V2.2 pass and reconciled line-by-line in `21_MASTER_PLAN_RECONCILIATION.md`. Outcome: **KEPT** — the destination stack (Next.js/Supabase/Cloudinary/Vercel/Expo-later), all §3 non-negotiables except two refined below, the rendering matrix, DAL/RLS/Edge-Fn architecture, Cloudinary rules, SEO/multilingual/RTL rules, JS-reduction plan, forms/security/testing/cutover requirements, mobile-readiness boundaries, and all ten §27 anti-patterns. **MODIFIED** — design-change rule (refined into the 5-way rule, Constitution §1), DB-change rule (justified-additive policy, Constitution §4), Broadcast stance (revisit-conditioned, ADR-06), tag keys (slug not id), Web-Vitals gate (+INP), chat/notif initial-state nuance. **SUPERSEDED** — the two-stage Compatibility→Native strategy (ADR-02: Freeze-and-Reconstruct; the compat stage would port the condemned i18n/auth/DataContext subsystems), the §5 folder tree (V2.1 [locale]/proxy/server-only structure authoritative), and the §24 phase model (replaced by P0→P1→ROUTE→P1B→P2..P7+FINAL). The Control Pack (V2.2) is the final source of truth because it post-dates the plan, is grounded in two adversarial repository audits + live production evidence (GC reports, sitemap, storage estate) the plan did not have, and encodes every kept plan rule as an enforceable gate rather than prose. The plan remains a historical planning input where not superseded and never overrides a newer explicit ADR.

**ADR-19 — Next.js 16 Cache Model.** Q: Cache Components (`use cache` + `cacheTag` + `cacheLife`) vs legacy model (cached fetch / `unstable_cache` / route `revalidate`). Decision: **Cache Components as the single primary model.** Rationale: targeting Next 16 makes the legacy mix (`unstable_cache`) the deprecated path; Supabase DAL calls are not `fetch`-cacheable, so `use cache` on DAL functions with `cacheTag(...tags)` + `cacheLife` profiles is the coherent mechanism. Rules: DAL functions in `server/dal/*` are the ONLY cache owners; tags attach inside DAL via `cacheTag`; TTL via named `cacheLife` profiles (catalog ≈1h, legal ≈1d) replacing route-level `revalidate` constants; dynamic personal routes never use `use cache`; new slugs resolve on-demand (with or without `generateStaticParams` — keep `generateStaticParams` for known slugs as build warm-up only, correctness never depends on it); delete → invalidate tag → DAL returns null → `notFound()` (real 404). Invalidation semantics: catalog defaults to stale-while-revalidate; **admin-edited entities require fresh-on-next-request** — use the current non-deprecated `revalidateTag` invalidation form per the pinned Next 16 docs (verify exact signature at FOUND-035; the deprecated one-argument usage is banned). Mixing models is a review-blocking violation; `06` §Hard Rules updated. Tests: CACHE-MODEL suite (CACHE-005). Revisit: only via ADR if Cache Components hit a hard limitation in P2.

**ADR-20 — Server Identity Verification Method.** Q: `getUser()` everywhere vs `getClaims()`. Decision: **`getClaims()` (locally verified JWT) for session-presence protection on server reads and layout gates; `getUser()` only where the fresh Auth record itself is needed** (MFA/AAL assertions before destructive ops, account pages showing auth-level data); Eventies authorization (role) always resolves from the `profiles` DB row regardless of method — claims are never trusted for role. Performance rationale: per-request Auth-server round-trips on every RSC read are unnecessary when RLS re-authorizes at the data layer anyway. Amends `07` wording ("every protected server read: getUser()"). Tests assert: revoked session fails claims verification after expiry window; role revocation effective per ADR-22 semantics below.

**ADR-04/05/09 amendments — Trusted boundary for destructive/admin operations.** The admin **layout gate is an early UX/security screen, never the authoritative enforcement**. Every sensitive operation must be enforced at its trusted boundary per the new `05` §Destructive-Operation Boundary Matrix: (A) the RPC itself verifies AAL2/recent-auth (via auth.jwt() claims inspection or passed-and-verified assertion pattern decided in SEC-016 design), (B) RLS enforces assurance level where expressible, or (C) client EXECUTE is revoked and the op moves behind a Route Handler/Edge Fn that independently verifies identity+role+AAL+recent-auth. UI confirmation, layout gates, and client wrappers are **not** enforcement. Blocking BYPASS tests call each operation directly (raw RPC/REST, no UI) and must be denied. ADMIN-003/SEC-016/DBMIG-010 implement; QG-P6 updated.

**ADR-21 — Cloudinary upload constraint enforcement (corrects SEC-012 assumption).** Signing arbitrary params does not guarantee Cloudinary enforces them; enforcement must use **verified mechanisms**: a **signed upload preset** defining `allowed_formats` and `max_file_size` (server-side enforced by Cloudinary), signer authorizes only that preset + whitelisted folder; client pre-validation is UX only. Negative test UPL-NEG: oversized/banned-format upload → Cloudinary rejects → no DB row → no orphan. Updates 05/10/ADMIN-015/SEC-012.

**ADR-23 — Cache model amendment: traditional model for real HTTP 404s (owner-approved, 2026-07-11; invokes ADR-19's revisit clause).** Q: Next 16 `cacheComponents`/PPR always commits a 200 streaming shell before a dynamic `notFound()` can run (verified against the pinned build + official docs `loading.md`: "the status code cannot be updated after streaming started"; the only real-404 paths are a proxy existence-check or non-PPR rendering). This is the "hard limitation in P2" ADR-19 named as its sole revisit trigger, and it directly blocks ADR-19's own stated goal ("delete → … → notFound() (real 404)") and the SEO-404/CAT-010 gate. **Owner ADR decision:** missing/deleted product and category routes MUST return a real HTTP 404; a route-specific exception from the cacheComponents/PPR model is approved where necessary; keep catalog data caching + tag revalidation wherever compatible; HTTP correctness for missing entities takes priority. **Implementation:** disable `cacheComponents` app-wide (Next rejects per-route opt-out while it is globally on, so the "route-specific exception" is realized at the only granularity Next 16 permits); DAL functions become the cache owners via `unstable_cache(fn, keyParts, { tags, revalidate })` — same tag registry (`server/cache/tags.ts`), same `revalidateTag(tag, …)` invalidation, same TTL intent (catalog ≈1h, daily ≈24h) as ADR-19; detail routes use `generateStaticParams` (warm-up) + `dynamicParams: true` + `revalidate`, so an unknown/deleted slug renders on-demand and `notFound()` returns a genuine 404. This retracts ADR-19's "`unstable_cache` is banned / Cache Components is the single model" mandate for the catalog read path ONLY, on the owner's authority; the tag-based ownership model, single-owner rule, no-cross-user-caching rule, and fresh-on-next-request admin semantics are all preserved. QG-ARCH-3 (no session import in cached scope) is unchanged and still enforced. Tests: CAT-010/SEO-404 (missing → 404) blocking; CACHE-005 conformance updated to the traditional primitives.

**ADR-22 — Auth revocation semantics (documentation ruling).** Reality the tests must assert (not an instant-revocation fantasy): refresh-token/session revocation prevents future refreshes; already-issued access tokens remain valid until expiry (≤ configured TTL); role revocation is effective immediately for server-checked reads (DB role lookup) and at next-request for RLS-guarded direct calls (token still valid but role row changed — RLS role checks read the profiles row via is_admin(), so effect is immediate at the DB); "sign out others" on password change revokes other sessions' refresh ability, not in-flight access tokens. `07` gains a Revocation Semantics section; AU-FLOWS assertions rewritten to these semantics.
